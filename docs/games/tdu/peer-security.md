# Native peer authorization and packet protection

Research provenance: these findings were produced in the sibling `tdu-server`
workspace. Runtime package paths below refer to Quetzal; `tools/`, private
`work/` evidence and Ghidra projects refer to that original research workspace.
Keep those private files there; Quetzal has no runtime dependency on them.
See [running.md](running.md) for current Quetzal operation.

This document covers the US PS2 `SLUS-214.90` build and verified MainGame overlay
from [analysis.md](analysis.md). The implementation is
`internal/games/tdu/peercrypto`. Quazal tickets, the edNet proxy tunnel, the native
`EncKey` association ticket and the downloaded `p2pkey` have separate roles.

## What the backend must provide

The native `EncKey` ticket is **generated by the initiating retail client** at
`0x151c40`. It is not a ticket the central server must issue for every peer
connection. Once authenticated Quazal identity and NAT/endpoint state are
available, the client creates a random field, serializes its own connection
descriptor and the intended receiving Quazal CID, seals them, and sends native
peer command 0. The receiving client validates that ticket at `0x152460`.

The revival backend must still provide real Quazal identities and usable
connectivity information, the native service/configuration path and compatible
`p2pkey` file bytes. Those dependencies let the stock clients execute their own
association and peer exchange paths. A server-side codec is useful for fixtures,
protocol inspection and any later explicitly designed relay/bridge, but issuing
an `EncKey` alone does not complete application login or session membership.

## The 130-byte EncKey ticket

Sender `0x151c40` invokes overlay encryption wrapper **`0xac5440`**.
Receiver `0x152460` invokes matching decryption wrapper **`0xac52c0`**.
The wrappers select `aes` and `sha256` from strings at `0x544b28` and
`0x544b2c`.

The cipher is **AES-256-CTR with a big-endian 128-bit counter**, beginning with
the supplied IV. It is not CFB, CBC, or TwoFish. This is supported by the
`ctr_start.c`, `ctr_decrypt.c` and `ctr_done.c` diagnostic strings, seven-argument
CTR initializer `0xab2a70`, and byte-wise counter increment in `0xab2d50`.
Mode 1 increments from the final counter byte toward the first; the initial
keystream block is AES(IV).

The encryption wrapper performs these steps:

1. HMAC-SHA256 the 82-byte plaintext using the same 32-byte protocol key used
   for AES.
2. Append all 32 HMAC bytes, producing 114 bytes.
3. Generate a fresh random 16-byte IV.
4. AES-CTR encrypt the 114 bytes; append the clear IV.

There is no padding. On receipt the wrapper splits off the last 16 bytes,
decrypts the first 114, recomputes HMAC over the first 82 plaintext bytes and
compares it with the following 32 bytes. The native compare routine is a normal
byte comparison; the Go codec uses `hmac.Equal` and does not expose plaintext
on failure.

| Ticket wire range | Content |
| --- | --- |
| `0..113` | AES-256-CTR ciphertext of body + HMAC-SHA256 |
| `114..129` | Clear 16-byte IV |

### Protocol key

The main ELF contains identical 32-byte seed copies at **`0x4e6e80`** and
**`0x4e6eb0`**. One is used by the receiving path and one by the sending path.
Both paths invert each byte and XOR the newly inverted byte into its predecessor.
Equivalently, the resulting key bytes are `seed[i] XOR seed[i+1]` for positions
0–30, followed by `NOT seed[31]`.

The resulting build-specific key is:

```
f9851f491a8bd6b8c7b21ee963a6584ea1d2c4cb4eda130ebc844f9b2d61cecd
```

`DefaultTicketKey()` returns that protocol constant. The key is embedded in every
copy of this build and is independent of the player's password, Quazal login
session key, proxy-tunnel AES key and downloaded 16-byte `p2pkey`.

### Plaintext field layout

All outer scalars are big-endian. The type tags are XOR-folded CRC-32 hashes of
exact strings: `EncKey` → `0x33bc`, and
`edNetClient::edNetClientV2()` → `0x269e`.

| Plaintext offset | Size | Field |
| --- | --- | --- |
| `0` | 2 | `EncKey` type tag `0x33bc` |
| `2` | 2 | Random-field byte count, 16 |
| `4` | 16 | Random bytes generated by the initiating client |
| `20` | 4 | Intended receiving client's Quazal CID |
| `24` | 2 | Nested descriptor byte count, 56 |
| `26` | 2 | Descriptor type tag `0x269e` |
| `28` | 4 | Initiating client's engine-format advertised address |
| `32` | 2 | Initiating client's advertised port |
| `34` | 2 | Additional descriptor scalar, preserved as `Flags` |
| `36` | 2 | Descriptor extension byte count, 44 |
| `38` | 44 | Raw PS2 descriptor extension |

The descriptor writer/reader are **`0x135c00` / `0x135b20`**. Constructor
`0x1362b0` initializes their shared type-tag global `0x5767c0` from the exact
string at `0x50fa06`. The separately named `edNetSessionClientV2` string nearby
initializes a different global and is not the descriptor embedded in EncKey.
`0x138b80` reads the length-prefixed random field, `0x1393c0` reads the recipient
CID and `0x138dc0` reads the nested descriptor.

The extension is copied as raw PS2 memory, so its numeric fields use
**little-endian** byte order even though the surrounding edNet stream uses
big-endian scalars:

| Extension offset | Size | Established role |
| --- | --- | --- |
| `0` | 4 | Extension format/type; normal Quazal-aware sender writes 2 |
| `4` | 4 | Initiating client's Quazal CID |
| `8` | 4 | Initiating client's local/LAN engine-format address |
| `12` | 2 | Local/LAN port |
| `14` | 1 | NAT-related byte |
| `15..43` | 29 | Other extension bytes, zero in the inspected initialization path |

Addresses are conventional IPv4 integer values: `192.0.2.1` is `0xc0000201`.
`0x26d5c8` parses the dotted octets, `0x26d598` returns their network-order
representation and `0x142fd0` byte-swaps that to the engine integer. Socket
sender `0x142c60` swaps it back before `sendto`. Thus Go callers can use
`binary.BigEndian.Uint32` on the four canonical IPv4 octets. The same integer
is serialized big-endian in the outer descriptor and copied little-endian in
the raw PS2 extension. The codec preserves every extension byte, and
`NewClientDescriptor` constructs the observed type-2 form.

### Receiver binding and association behavior

`0x152460` requires a ready Quazal connection and a ticket payload of exactly
130 bytes. After successful decryption it checks the type tags, parses the
random field and descriptor, then requires:

- The random field reader returns 16 bytes. The contents of that field are
  not compared against another nonce or the downloaded packet key.
- The intended recipient CID equals the receiving client's own registered
  Quazal CID from `0x1e23d0`.
- The descriptor has extension data and its extension type is greater than 1.
- The packet's source address matches the descriptor's advertised address or
  its local/LAN address.

The caller already associates packets with an expected source endpoint before
entering this ticket path. On success the routine installs the advertised/local
endpoints, substitutes the local address for an advertised loopback address when
needed, enters association state 4 and sends command 1. On failure it sends
command 2. The peer state machine, source-port checks, pending session membership
and NAT endpoint selection remain outside the crypto codec.

`Ticket.ValidateBinding` implements the local CID and source-address portion.
A ticket contains no recovered expiry field or replay counter, and its shared
client-side key does not prove a central server issued it. Future server or relay
code must retain authenticated account/session context rather than treating
successful decryption alone as account authorization.

The Go codec implements the normal fixed-size US format. It rejects noncanonical
lengths and tags instead of reproducing permissive/truncated malformed reads.

## Downloaded p2pkey and established peer datagrams

The required resource named **`p2pkey`** is requested by `0x4614b0`. Completion
callback **`0x4613c0`** clears 16 bytes at **`0x4e6e30`**, copies up to 16 bytes
from the successful nonempty resource result, then sets completion flag
`0xa9bf68`. Assembly at `0x461440` confirms the `min(size,16)` copy bound.

Those 16 bytes are used by **peer sender `0x152c80` and receiver `0x1520e0`**.
They do not replace the 32-byte EncKey ticket key.

A native peer datagram begins with:

| Offset | Size | Field |
| --- | --- | --- |
| `0` | 2 | Big-endian flags; bit 0 indicates XOR protection |
| `2` | 2 | Big-endian command, protected when bit 0 is set |
| `4` | variable | Command payload |
| final | 1 | XOR checksum for a protected datagram |

Commands observed by the receiver are 0 (EncKey association), 1 (accept),
2 (reject), 3 (close/reset path), 4 (application data) and 5 (reset path).
The codec's command names describe those branches, not recovered original enum
symbols.

In established association state 4, outgoing commands **3 and 4**:

1. Write clear flags `0x0001`, command and payload.
2. Append the bytewise XOR of every preceding plaintext byte, including flags
   and command.
3. XOR bytes **at absolute packet offsets 2 through the checksum byte** with
   `p2pkey[offset & 15]`.

The two flag bytes remain clear; the first protected byte uses key index **2**,
not zero. A period boundary in a long payload does not reset the key index.
The receiver reverses that operation, removes the checksum byte, verifies the
XOR, and rejects plaintext commands 3/4. Its bit-0 protection test ignores other
flag bits, which the decoder preserves.

`0x152b90` bounds established application payloads to less than `0x546`, so the
codec uses **1349 bytes** as its maximum payload. Packet construction performs
no session state transitions; callers must only send established data after a
successful association.

This wrapper is repeating XOR plus a corruption checksum, not cryptographic
authentication. Two equal bit changes can cancel in the checksum. A regression
test demonstrates that limitation so later code does not mistake successful
packet decoding for a verified user identity.

## Codec API and verification

The standard-library-only Go package provides:

- `EncodePacket` / `DecodePacket` for the native command header, XOR and checksum.
- `DefaultTicketKey`, `NewClientDescriptor`, `SealTicket` and `OpenTicket` for the
  fixed 130-byte EncKey ticket.
- `Ticket.ValidateBinding` for recipient CID and advertised/local source address.

`SealTicket` accepts an explicit IV to allow repeatable machine-code fixtures;
real callers must supply fresh random IV and random-field bytes.

```sh
scripts/go test ./internal/games/tdu/peercrypto
```

The tests cover a separately calculated packet vector across a key-period
boundary, clear and protected commands, mutation/length failures, packet buffer
ownership, the checksum's cancellation behavior, binding failures, every
single-byte ticket tamper location and authenticated malformed field layouts.
The fixed ticket fixture was independently generated with OpenSSL AES-256-CTR
and Python HMAC-SHA256. It is synthetic and contains no player capture data.
The package also verifies **54 synthetic vectors from the actual retail
`0x152c80` sender** under Unicorn: six commands across nine payload sizes from
0 through 1337 bytes. Only memory-copy/datagram-send calls are intercepted,
with scoped EE low-word ABI adaptations documented by `tools/ee_validation.py`.
The sanitized inputs/results are checked in as
`internal/games/tdu/peercrypto/testdata/native-packets.json`; no executable bytes or
player captures are included. This independently validates byte-for-byte
packet construction and decoding of those outputs.

Additional machine-code validation is tracked under ignored `work/validation/`.
The ticket currently has independent OpenSSL coverage; native ticket and retail
two-client gameplay validation remain separate.

Private Ghidra evidence is under `work/world-sessions/ps2/peer-ticket*.log` and
`peer-ip-*.log`,
with earlier sender/receiver traces under `work/gameplay/ps2/peer-key.log` and
`tunnel-state.log`. The overlay mappings were temporary and discarded on close.

## Identity clarification from the native caller

Getter `0x1e23d0` supplies the registered connection CID from context `+0x0c`;
the account PID getter is `0x1e23a0` at `+8`. The EncKey recipient scalar and
descriptor extension both use **CID**, not account PID. Receiver `0x152460`
compares its recipient with `0x1e23d0`, and sender `0x151c40` populates the
extension from that same getter. This corrects earlier field names without
changing a wire byte or granting account authority. Go uses
`Ticket.RecipientConnectionID` and `ClientDescriptor.ConnectionID()`.
